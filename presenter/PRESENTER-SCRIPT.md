#### S7 · Three ways to run GitHub Enterprise

*⏱ 4 min · running 0:16 → 0:20*

> 👁 **SHOW** Three cards: GitHub Enterprise Cloud, GHE.com data residency, GitHub Enterprise Server.

GitHub Enterprise comes in two offerings, and the cloud offering comes in two flavors.

Cloud first. Software as a service, minimal configuration, private but on the internet. This is where every new capability lands first, and sometimes only. The hierarchy is enterprise, organization, team, repository. Accounts belong to the person, except with Enterprise Managed Users, which we will get to in two slides.

The second card is the same cloud, in your region. GitHub Enterprise Cloud with data residency, called GHE.com, is generally available in four regions. The EU, which since May 1 this year also includes Azure regions in Norway and Switzerland. Australia. The US. And Japan, GA since December 18 last year. Each enterprise gets a dedicated subdomain on ghe.com. It always uses Enterprise Managed Users, and there are no public repositories. If someone asks about moving from Server to GHE.com, the answer is Enterprise Live Migrations, GA since September 1.

The third card is Server. On your network, self-managed, self-maintained, high-availability capable. Actions, Packages and Advanced Security all run on it.

Both are built to enterprise security standards. What differs is who owns the hardening. On Cloud that is GitHub. On Server it is your team. People assume on-premises means more secure. It means you do the patching.

One dated change on the purple callout. Since October 7, GHE.com rejects TLS clients that only offer X25519. If a corporate proxy or an old build agent stopped connecting to your ghe.com subdomain this month, that is why.

#### S9 · Enterprise Managed Users

With EMU, the identity provider controls usernames, profile data, team membership and repository access. Managed user accounts can contribute only to private and internal repositories in their own enterprise, and to their own private repositories. They cannot create public content. #### S10 · GitHub Enterprise Server

*⏱ 3 min · running 0:25 → 0:28*

Server is self-hosted infrastructure on your network, with isolated accounts, and it needs maintenance. Older decks said "near feature parity with Cloud". That is not true any more, and I would rather you hear the verified examples than a slogan.

GitHub Copilot is not available for Server. Release 3.22 adds only a technical preview of Copilot CLI with a self-configured model provider for air-gapped sites. GitHub Code Quality is not on Server. The Security and quality navigation is not on Server. And Server does not hold potentially malicious workflows for approval the way the cloud does.

Operating it. You keep it upgraded, and since August 18 GitHub refuses support bundles from appliances below the listed patch levels, so an old appliance also loses support tooling. The current release is 3.22, GA September 8, and it does bring enterprise teams.

Migration paths, if that is where you are headed. Enterprise Live Migrations from Server to GHE.com. GitHub Enterprise Importer with GitHub-owned blob storage, GA since November 2025, which removes the "bring your own storage bucket" step. And the Importer from GitLab, GA August 3.

When is Server still the right answer? Regulatory isolation that data residency cannot meet, or an air-gapped network. Otherwise the cloud is where the roadmap goes first.

#### S15 · From enterprise policy to repository role

> 🎬 **DO** Walk the left column top to bottom, then the roles column, then the two feeders on the right.

Start at the top. The enterprise has policies. A policy controls the options an organization has. You can leave it unenforced, so each organization owner decides. Or you can enforce one value across every organization. Base permission is the classic example: enforce Read everywhere, or let each owner choose. By default, no enterprise policy is enforced.

The organization has settings. It can add restrictions. It cannot weaken a value the enterprise enforced.

The repository has settings. Same rule again. If a repository admin cannot find a setting, it is usually set, and locked, one level up.

Now the roles column, and these are the current ones. Enterprise roles: enterprise owner, billing manager, app manager, security manager, which is in public preview, and custom enterprise roles. Enterprise members are organization members or unaffiliated users. Guest collaborators exist only with managed users.

Organization roles: owner, member, moderator, billing manager, security manager, GitHub App manager, and predefined roles such as CI/CD admin. And custom organization roles. Since February 23 this year, the enterprise can define a custom organization role once and organization admins assign it everywhere.

Repository roles: Read, Triage, Write, Maintain, Admin, plus custom repository roles.

Two feeders on the right. Enterprise teams, defined once at the enterprise, assigned into organizations, roles, licenses, cost centers and bypass lists. Organization teams, the ones you nest and use in CODEOWNERS. And collaborators: outside collaborators in a personal-account enterprise, repository collaborators with managed users. Outside collaborators do not go through SSO; that remark applies only to personal-account enterprises.

Two arrows into the repository roles show how people get them. Team permissions, when a team is granted a role on a repository. And individual access, when a person is granted one directly.

#### S16 · More than one organization

*⏱ 2 min · running 0:40 → 0:42*

Each organization is a silo. Its own settings, roles, teams, at-mentions and search. All of them inherit the enterprise policies. Separate SAML per organization is possible only in a personal-account enterprise that does not enforce SAML at the enterprise; enforcing it at the enterprise applies one configuration everywhere, and managed-user enterprises authenticate the whole enterprise through one IdP anyway.

Now the guidance, because it changed in October 2025 and a lot of us still quote the old version. The old advice was "one organization". GitHub's current page, Best practices for organizing work in your enterprise, says five things.

Use organizations to group related work, or similar governance requirements. Create organizations intentionally; in GitHub's words, don't try to fit unnatural pieces of your company together into a single large organization. Start with a small number and add as the need arises, because adding is easier than removing. At-mentions and search still work best inside one organization. And use enterprise teams and roles to organize people at scale.

So the new sentence is: as few as make sense, and on purpose.

Visibility here means the repository's own setting combined with the base permission set at the organization or the enterprise. Three values.

Public: anyone on the internet. Enterprises with managed users, and so every GHE.com enterprise, cannot create public repositories at all.

#### S20 · Repository roles

*⏱ 2 min · running 0:48 → 0:50*

Five built-in roles, from least access to most.

Read is read-only on code and Actions. Read users can submit and comment on issues, pull requests and discussions. It is for non-code contributors who want to follow or discuss the project.

Triage is Read plus managing issues, pull requests, discussions, assignments and labels. For the people who organize work without pushing code: product managers, support, community managers.

Write is everything except repository settings. That is your standard developer role.

Maintain adds some settings: topics, enabling features, configuring merges and Pages, and pushing to protected branches. For project leads who manage the repository without sensitive or destructive actions.

Admin is everything, including access, rulesets, security settings and deleting the repository. Keep it rare.

Custom repository roles fill the gaps, up to five per organization. Lab 9 builds a contractor role and a security-reviewer role.

Now tie it back to the diagram. Every member starts at the organization's base permission. If someone with admin access grants a member a higher role, directly or through a team, the higher role wins. Organization owners have Admin on every repository the organization owns.

The most common mistake I see is Admin everywhere. If someone needs to push and configure Pages, that is Maintain. If they need to push, that is Write.

#### S31 · SSO and credentials

*⏱ 4 min · running 1:39 → 1:43*

Two layers of authentication: the GitHub sign-in, then your identity provider. Which protocol depends on the platform. Personal-account enterprises use SAML at the organization or the enterprise; enforcing it at the enterprise applies one configuration everywhere. Managed-user enterprises use SAML or OIDC, and OIDC is Entra ID only, which is what lights up Conditional Access. Server uses SAML, LDAP or CAS.

Two-factor authentication is mandatory for contributors on github.com. It is not required for managed users or Server users, who authenticate through the IdP or the instance. Prefer phishing-resistant methods: passkeys and security keys.

Now, what needs SSO authorization. Personal access tokens, classic and fine-grained, and user SSH keys: yes, every one, per organization. Since September 16, an enterprise with enterprise-level SSO can let an enterprise-installed GitHub App authorize an existing classic token or SSH key for up to fifty organizations in one call, instead of each developer clicking through organization by organization. #### S33 · Why teams

*⏱ 2 min · running 1:45 → 1:47*

Four reasons to run everything through teams.

Collaboration. Teams are central to GitHub's collaboration features, like team at-mentions, which notify the right group that you want their input. A team can be project-focused or subject-focused, and it can map to job titles or roles.

Innersource. Helping your teams discover, customize and reuse internal projects: code, documentation, shared CI. That lowers cost, adds flexibility, and ends vendor lock-in between your own departments.

Onboarding and offboarding. Instead of adding or removing a person on each repository, you put them on the right team. The team stays assigned to the right repositories. Leaving the team revokes access everywhere. Less work, and less risk.

Security. You grant Read, Write and Admin to groups, not individuals. And teams work in CODEOWNERS files to define and automate pull-request review.

Three kinds of team work well. Organizational units that mirror the company. Product teams, which keep notifications, CODEOWNERS and reviews close to the maintainers. Interest teams around a topic, technical or not. And one all-employees team for global announcements.

#### S35 · Team membership from your identity provider

*⏱ 3 min · running 1:50 → 1:53*

Three ways to fill a team, and which one you use depends on the kind of enterprise.

Team sync, for enterprises with personal accounts. You connect a GitHub team to an IdP group in Microsoft Entra ID, commercial tenants only, or Okta. Membership updates as the group changes. Up to five groups per team; groups over five thousand members are not supported. A parent team cannot be synced: if the team you want to connect is a parent, create a new team or remove the nested relationship. Team sync works with organization teams only, and when SAML is enforced at the enterprise it is managed for the whole enterprise.

SCIM groups, for managed-user enterprises. Team sync is not used with EMU at all. Instead, the IdP's SCIM groups map to organization teams and to enterprise teams, and a group change can add or remove organization access and Copilot licenses in one go.

And manual membership, through the web UI or the API. Fine for a small organization, a liability at scale, and any manual edit to a synced team is overwritten at the next sync.

Naming tip: prefix the synced groups in your IdP, GH dash engineering dash frontend, so people can see which groups drive GitHub access, and keep the parent-child structure in GitHub.

#### S40 · The audit log

*⏱ 4 min · running 2:20 → 2:24*

Last presentation block of the day: the audit log, and the users who have stopped using their license.

The audit log captures settings changes, membership changes, repository actions, app permissions, authentication events, billing events, and Git events. The enterprise audit log aggregates every organization, which is one of the quiet benefits of having an enterprise account.

Retention is the detail that matters. Web events are kept for one hundred eighty days, in the UI and the API. Git events, clone, push and fetch, are kept for seven days, and only through the API. I will say that again, because it ends investigations: Git events last seven days.

The right column has the four queries you will use most: who created repositories, who changed a base permission, every ruleset and branch protection change, and enterprise team changes. You can export CSV or JSON. The API paginates with a cursor and allows seventeen hundred fifty requests an hour.

#### S41 · Streaming to your SIEM

*⏱ 3 min · running 2:24 → 2:27*

Audit log streaming is an enterprise feature that forwards events in near real time. The targets are Splunk, Azure Event Hubs, which is how you reach Microsoft Sentinel, Azure Blob Storage, Amazon S3, Google Cloud Storage and Datadog. You can stream to two endpoints at once. There is no generic HTTPS target.

The guarantees. Delivery is at-least-once, so your consumer must tolerate duplicates. Payloads are compressed JSON. If a stream is paused, events buffer for seven days and then drop. GitHub health-checks the stream every twenty-four hours, and a misconfigured stream is disabled after six days. Put that in your runbook: a stream that breaks on a Friday needs attention by Thursday.

If you do not have enterprise streaming, there is a workaround. A scheduled workflow that calls the organization audit-log API daily and archives the output to your own storage. Lab 8 builds the exact command.

Why it is not optional: SOC 2, FedRAMP and HIPAA retention requirements exceed one hundred eighty days, and real-time alerting on a new owner or a ruleset bypass only happens in a SIEM.

#### S42 · Dormant users

*⏱ 3 min · running 2:27 → 2:30*

A user is dormant after thirty days without qualifying activity. The window is fixed.

What counts: signing in through SAML or the web, creating a repository, pushing to an internal repository over HTTPS, and the collaboration actions: issues, pull requests, comments, labels, releases, stars, wiki pushes.

What does not count, and this is the list that matters. Anything done with a personal access token, an SSH key or a GitHub App. Git operations on private repositories. Browsing without interacting. And public activity outside the enterprise.

So a developer who pushes to private repositories over SSH every single day can appear dormant. And a CI service account always will.

The reports are under Enterprise, People, Dormant users, and under Compliance, Reports, as a CSV. The process that works: report monthly, exclude service accounts and bots, warn the person, give a grace period of a week or two, then remove. Lab 10, self-paced, scripts the organization-level version and designs the reclamation workflow.

#### S53 · Rulesets replace branch protection

*⏱ 3 min · running 0:31 → 0:34*

> 👁 **SHOW** The comparison table, then the dated callout.

Seven rows, and the first two decide it.

Scope. A branch protection rule lives in one repository. A ruleset lives in a repository, an organization or the enterprise, so one definition covers hundreds of repositories, including the ones created next week.

Enforcement. Branch protection is on or off. A ruleset is Active, Evaluate or Disabled. Evaluate is the dry run: the rules are checked on real traffic, nothing is blocked, and every result lands in Rule insights. That one mode is why migrations stop being scary.

Targets. Branches only, versus branches, tags and pushes. Tag rulesets protect your release markers. Push rules restrict file paths, extensions and sizes.

Layering. One rule per branch pattern, versus as many rulesets as you need on the same branch. When several apply, the strictest combination wins. Nothing relaxes anything.

Bypass. With branch protection, admins override and the trail is thin. With rulesets you name the actors, you pick Always or Pull requests only, and every bypass is logged.

Visibility. Branch protection is for admins. Active rulesets are visible to every contributor, so a blocked developer can read why.

Audit and portability. Rule insights, and JSON export and import, so a ruleset is a file in version control.

The two coexist. Both are evaluated on every push and every merge, and the strictest combination applies. The risk is not security; it is a developer who cannot tell which rule blocked them.

The dated callout is the migration path. Since August 11, Settings, Branches has a Convert to ruleset button next to each classic rule. GitHub maps required reviews, status checks and push restrictions into equivalent ruleset rules and shows the new behavior before you pick a status. Active is the default; pick Evaluate for a first migration. One rule does not map one to one: conversation resolution lives inside the pull request rule. When the page says rulesets fully cover the old rule, delete it. Use conversion for repository rules; for policy that spans repositories, build organization rulesets.

#### S65 · The cost model

*⏱ 3 min · running 1:37 → 1:40*

Three tiles, and the third one is the whole model. Nineteen for Secret Protection, thirty for Code Security, per active committer a month. An active committer is anyone who pushed at least one commit in the last ninety days to a repository where the product is enabled.

#### S69 · REST and GraphQL

*⏱ 2 min · running 2:03 → 2:05*

Both APIs are shipped and supported. There is no published deprecation roadmap for REST, so do not promise one. Pick the API you know, or the one that has the endpoint you need. Actions, for example, is REST only.

The left column is REST. It is calendar-versioned, and you pick the version with the X-GitHub-Api-Version header. 2026-03-10 is the newest version and the first with breaking changes. 2022-11-28 is still the default when you omit the header, and it stays supported for at least twenty-four months. So nothing broke on March 12 when the new version shipped. Things break when a script omits the header and the default moves. Put the header in every script.

The right column is GraphQL. One POST to slash graphql with a query or a mutation. You ask for nested data and get back only the fields you named. Two dated changes. Since September 1, 2025, GitHub caps execution resources per query, so a query that walks every repository and every collaborator is rejected rather than slow. And the GraphQL Explorer inside the docs was removed on November 7, 2025. Use gh api graphql, which is what Lab 13 does.

The table at the bottom is the rate limits, one number per credential. A personal access token, or an OAuth token, gets five thousand requests an hour per user. GITHUB_TOKEN in a workflow gets one thousand an hour per repository, or fifteen thousand against Enterprise Cloud resources. Handle the rate-limit response in every script; the reference card has the one-liner that shows what you have left.

#### S70 · Credentials: read the prefix

*⏱ 3 min · running 2:05 → 2:08*

> 👁 **SHOW** Four cards, one per credential type, with the token prefix on the first line of each.

The prefix tells you what you are looking at, so let us read the cards left to right.

Personal access tokens. github underscore pat underscore for fine-grained, ghp underscore for classic. They are for personal use: scripts, local debugging, one-off calls. Never for a service the company depends on, because the token leaves with the person. Prefer fine-grained. Enterprise policy can restrict classic tokens, require approval for fine-grained ones, and cap the lifetime; the default maximum for fine-grained tokens is 366 days. Tokens unused for a year are revoked automatically.

OAuth Apps, gho underscore. They act as the user who authorized them and share that user's five thousand an hour. They remain for identity-provider style sign-in and the few things a GitHub App cannot do. Since August 14, OAuth apps can issue eight-hour access tokens with six-month refresh tokens; on by default for new apps, opt-in for existing ones. GitHub's own docs say it: in general, GitHub Apps are preferred over OAuth apps.

GitHub Apps, the green card, and the recommended choice. Three prefixes. ghu underscore is a user access token, eight hours. ghr underscore is its refresh token, six months. ghs underscore is an installation token: one hour, its own identity, fine-grained permissions, no license consumed, fifteen thousand requests an hour on Enterprise Cloud. One change to know. Installation tokens are now stateless JWTs of about five hundred twenty characters, and the rollout finished on October 2. If an integration checked token length, or stored tokens in a forty-character column, it is already broken. Treat tokens as opaque strings.

GITHUB_TOKEN, also ghs underscore, because it is an installation token too. GitHub mints one per job, it expires when the job ends, and events it causes do not start new workflow runs. Inside Actions, use it first.

The purple callout covers the rest. Deploy keys are SSH keys scoped to one repository, read-only unless someone ticks write access, and they do not go through SSO. Machine users are ordinary accounts owned by nobody; keep their credentials in a shared secret store. Both are hit by the SSH hardening. New RSA keys must be at least 3072 bits since October 14. ssh-rsa SHA-1 signatures get brownouts on November 4 and December 9 and are removed on January 13. Ed25519 keys are unaffected, so that is the guidance to send out. And the temporary stateless-token header is deprecated on November 30.

#### S80 · Privacy, licenses and repository health

*⏱ 5 min · running 2:50 → 2:55*

Three cards, five minutes, and each one has a lab or a doc behind it.

Privacy and data residency first. GitHub Enterprise Cloud with data residency runs on your own subdomain of ghe.com, in four regions: the EU, Australia, the US and Japan. It is always managed users and there are no public repositories. Code, issues, Actions data and personal data stay in the region. Some data does not: billing, support cases and pseudonymized telemetry. And Copilot data stays in-region only when you enable the policy Restrict Copilot to data residency compliant models, which exists for the US and EU regions and costs ten percent more AI Credits. It is off by default. On the user side, people control their profile, whether private contribution counts show, and the noreply email address for commits. IP addresses appear in the audit log only when an enterprise owner enables disclosure. Doc 26 has the full data-boundary tables.

Seats, the orange card, because the invoice is where this topic becomes real. A license is consumed by every organization member, owners included. By every outside collaborator on a private or internal repository. By dormant users who are still members. And, outside EMU, by pending invitations. Not consumed: unaffiliated users, billing managers, suspended managed accounts, and guest collaborators who are in no organization. One person consumes one license across every organization and every Server instance in the enterprise. So the two levers are the dormant-user cleanup, Lab 10, and a hard look at who your outside collaborators are.

Repository health, the third card. Keep a repository under a gigabyte. Git warns at fifty mebibytes per file and blocks at one hundred. When large files are already in history, git-filter-repo is the tool GitHub and the Git project recommend; filter-branch is deprecated and BFG is legacy. After the rewrite, track the big binaries with Git LFS so it does not happen again, and remember that a rewrite invalidates every clone, so coordinate the force push. Stale branches: turn on Automatically delete head branches, in the repository settings under Pull Requests; it prevents most of the pile. And the end of life. Archive keeps everything read-only, searchable and forkable, and that is the default for anything someone might reference again. Transfer moves the repository and its history to another owner, with redirects. Delete only for repositories created in error, or when sensitive data cannot be purged any other way. Lab 14 runs the whole diagnosis.
